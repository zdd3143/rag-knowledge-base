**八个核心发现**（详见「实验与发现」与「评估结果」）

1. 整份文档不能直接当向量——会被**静默截断**
2. 纯向量分不清「答案」和「看起来像答案的东西」，**分差仅 0.02**
3. BM25 能补上，但中文必须加**领域词表**
4. **样本量决定结论**：同一套脚本，5 条样本 vs 32 条样本，四个配置的优劣**全部翻转**
5. **融合不总是正收益**：纯 BM25 在事实型问题上 Hit@5 达 0.889，融合后反而**降到 0.778**
6. **口语化改写是真实短板**：8 条改写问题，**所有配置都过不了 0.4**
7. **三次「看起来是 A，其实是 B」**——归因比调参重要
8. 语料质量是天花板：PDF 表格提取会产出**「竖排数字粥」**

## 这是什么

输入企业年报 PDF，能对里面的内容提问，输出**带引用来源、可溯源、不确定时拒答**的答案。

```
问题
  ↓
┌──────────────── 检索 ────────────────┐
│  向量检索 Top-50 ┐                    │
│                  ├─ RRF 融合 → Top-20 │
│  BM25   Top-50 ┘                      │
└───────────────────────────────────────┘
  ↓
cross-encoder 重排 → Top-5
  ↓
拼装带编号的参考资料 → 调用 LLM → 答案 + [1][2] 引用
```

## 为什么不用 LangChain

市面上 99% 的 RAG 项目是 `LangChain + Chroma + 一句话调用`，看不出任何工程细节。

这个项目**刻意不用框架**，每个环节自己实现：

- BM25 是手写的（倒排索引 + 正 IDF 变体），不是调库
- 分块、融合、引用解析全部自己实现
- 每一步都配**对照实验**，而不是"调完感觉变好了"

**目标不是做出一个能跑的 demo，而是搞清每个设计为什么存在。**

## 实验与发现

> 这一节是项目的重点——不是「写了多少代码」，而是「验证了什么、修了什么」。

### ① 整份文档不能直接当向量

BGE-M3 最大输入 8192 token，25 万字的年报会被**静默截断**。

**实测**：整份年报的向量，与「只取前 8000 字」的向量相似度高达 **0.999**——
说明 8000 字之后的内容压根没进模型。

→ **必须分块**，否则模型只是在拿"年报的封面"回答问题。

### ② 纯向量检索分不清「答案」和「看起来像答案的东西」

问题「中国石油2023年的营业收入是多少？」：

| 排名 | 块内容 | 相似度 |
|---|---|---|
| 1 | 一张无关的子公司持股表 | **0.7404** |
| **16** | **正确答案所在块** | **0.7189** |

**分差只有 0.02（相对 3%）。**

原因是两块都是「中文财务文本 + 大量数字」，纯向量模型看的是"整体语义像不像"，
**看不出「这一段在回答问题，那一段只是在列表格」**。

### ③ BM25 能补上，但中文分词是前提

手写 BM25（倒排索引 + 正 IDF）后，正确答案从第 16 名升到第 **4** 名。

但 jieba 把「营业收入」切成「营业/收入」、「中国石油」切成「中国/石油」，
**两个最有区分度的词都废掉了**。

加入 19 个石油财务领域词后：

| 词 | 出现在多少块 | IDF |
|---|---|---|
| `营业`（被切碎） | 45 | 3.326 |
| **`营业收入`（加词后）** | **62** | **3.008** |
| `的` | 1095 | 0.145 |

排名随之升到第 **2**。

### ④ IDF 是相对的，不是词的固有属性

`中国石油` 在当前语料里 IDF 只有 **0.794**——因为它出现在 **45%** 的块里。

**因为语料只有它一家的年报，公司名到处都是。** 语料换成 30 家公司后，它自然会变成稀有词。

> **结论**：IDF 衡量的是「这个词在你的语料库里有多稀有」，而不是词的固有重要性。

### ⑤ RRF 融合成功：16 → 2 → 1

| 阶段 | 目标块排名 |
|---|---|
| 纯向量 | 16 |
| BM25 | 2 |
| **RRF 融合** | **1** |

**为什么 RRF 用排名而不用分数**：向量分数是余弦相似度（0~1），BM25 分数无上界（这里到 11），
**两者量纲完全不同，相加毫无意义**。

RRF 公式：`score(doc) = Σ 1 / (k + rank)`，k=60。
它只看"排第几"，因此天然免疫量纲问题。

**核心性质**：一路的第 1 名，比不过两路都还不错的选手。

### ⑥ 工程优化：numpy 矩阵化，提速 325 倍

| 实现 | 检索 1265 块耗时 |
|---|---|
| 纯 Python 循环 | **156.4 ms** |
| numpy 矩阵乘法 | **0.48 ms** |
| 提速 | **325 倍** |

**原因**：Python 循环慢的不是"算得慢"，而是**逐元素的对象创建和解释器开销**。
`vecs @ q` 一次算完所有相似度，走 C 循环 + SIMD。

> 这是**工程优化**而非算法优化——还是暴力算全部，只是让同样的计算跑得更快。

### ⑦ 三次「看起来是 A，其实是 B」⭐

| 表面现象 | 查证后的真因 |
|---|---|
| 纯向量检索不到答案 | 不是模型不行，是**排序**问题（答案排第 16） |
| BM25 效果不理想 | 不是算法问题，是 **jieba 把「营业收入」切碎了** |
| 重排把正确答案从第 1 打到第 7 | 不是重排坏了，是**被排到前面那块确实高度相关**——它是财务报表里的「营业收入附注」，只是不含我们指定的那个总数 |

> **任何「变差了」都要先归因再动手。**
> 用单个样本判断优化好坏是不可靠的——这正是需要评估集的原因。

### ⑧ 语料的真实质量问题：PDF 表格提取

`page.get_text("text")` 不理解表格结构，把财务表格压成**竖排数字粥**：

```
505
-
1,285,752
-
-
1,350,257
合计
151,150
336,861
```

表头与数据行被冲散、表格被切块拦腰砍断。
**这是「数字碎片污染检索」的真正源头——不是模型笨，是语料本身就是坏的。**

> 待办：改用 PyMuPDF 的表格提取 API，或用「数字占比」过滤这类块。
> **但需要先有评估集，才能验证改动是否真的有效。**

### ⑨ 拒答机制：最容易被忽略的一环

提示词写死三条规则：**只用给定资料、必须标引用、没有就明说「无法回答」**。

实测 4 个问题：

| 问题 | 结果 |
|---|---|
| 营业收入是多少 | ✅ 答对 + 引用可溯源 |
| 净利润是多少 | ✅ 答对 + 引用可溯源（经逐字核对）|
| 西南石油大学的校训 | ✅ **正确拒答** |
| 量子纠缠的贝尔不等式 | ✅ **正确拒答** |

**关键认知**：拒答率高不是模型问题，是**检索问题**——
大模型只能看到检索交给它的 5 个块，漏了就只剩拒答或编造两个选项。

### ⑩ 引用是双刃剑

引用机制让答案**可核查**，但也给幻觉**背书**——
一个格式规范、带出处、精确到小数点后两位的假答案，比裸的胡编更容易骗过人。

> **所以引用必须可验证**：答案里的数字，要能在被引用的块里**逐字找到**。
> 这个检查应该自动化（阶段 7）。

## 评估结果（阶段 7）

> 完整数据见 [docs/评估结果.md](docs/评估结果.md)。38 条评估集，**32 条参与检索评估**。
> 所有数字可复现（重跑结果完全一致，无随机性）。

### 总表

| 配置 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | MRR |
|---|---|---|---|---|---|
| 纯向量 | 0.0312 | 0.1250 | 0.2500 | 0.3438 | 0.1268 |
| **纯 BM25** | 0.2812 | **0.5938** | **0.7188** | 0.7500 | 0.4534 |
| RRF 等权(0.5/0.5) | 0.2812 | 0.4375 | 0.4688 | 0.5938 | 0.4041 |
| 加权(0.4/0.6) | 0.3125 | 0.4375 | 0.5000 | 0.6250 | 0.4222 |
| 加权(0.3/0.7) | 0.3438 | 0.4375 | 0.4688 | 0.7188 | 0.4374 |
| 加权(0.2/0.8) | 0.3125 | 0.4375 | 0.5312 | 0.7500 | 0.4374 |
| **加权(0.3/0.7)+重排** | **0.4375** | **0.5938** | 0.6562 | **0.7812** | **0.5445** |

### 按问题类型细分（Hit@5 / MRR）⭐

| 配置 | factual(n=18) | multi_hop(n=6) | paraphrase(n=8) |
|---|---|---|---|
| 纯向量 | 0.278 / 0.153 | 0.333 / 0.125 | 0.125 / 0.069 |
| 纯 BM25 | **0.889** / 0.577 | **0.667** / 0.377 | 0.375 / 0.232 |
| RRF 等权(0.5/0.5) | 0.611 / 0.514 | 0.333 / 0.329 | 0.250 / 0.214 |
| 加权(0.3/0.7) | 0.611 / 0.556 | 0.333 / 0.294 | 0.250 / 0.278 |
| 加权(0.2/0.8) | 0.667 / 0.537 | 0.333 / 0.337 | 0.375 / 0.288 |
| **加权(0.3/0.7)+重排** | 0.778 / **0.695** | **0.667** / 0.376 | **0.375** / **0.332** |

### 三条结论

1. **纯 BM25 在事实型问题上碾压一切**（Hit@5 **0.889**）。
   把只有 0.278 的向量检索融合进来，**是负收益**——降到 0.778。
2. **口语化改写全体崩盘**（最高 0.375，向量最低 0.125）。
   注意：**向量在改写问题上比在事实问题上还差**（0.278 → 0.125），
   这与"向量擅长同义泛化"的教科书直觉相反。
3. **没有任何配置全面胜出**：Hit@5 最优是纯 BM25，MRR / Hit@10 最优是加权+重排。
   **"最优配置"这个问题问错了**——正确的问题是
   **"在什么 top_k 下、以什么指标为目标时，哪个配置最优"**：

   | 喂给 LLM 的块数 | 该选谁 | 依据 |
   |---|---|---|
   | top-5 | 纯 BM25 | Hit@5 0.7188 > 0.6562 |
   | top-10 | 加权(0.3/0.7)+重排 | Hit@10 0.7812 > 0.7500 |

## 快速开始

### 1. 环境

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1          # Windows
pip install -r requirements.txt
python src/check_env.py             # 自检
```

> ### 想要 GPU 加速（可选，但强烈建议）
>
> PyPI 上的 Windows torch 是 CPU 版。实测 CPU 下 `/search` 要 **12.4 秒**，
> 换成 CUDA 版后降到 **0.85 秒**。
>
> ```powershell
> pip install torch --index-url https://download.pytorch.org/whl/cu126
> ```
>
> ⚠️ 官方源国内很慢（实测单连接 **0.46 MB/s**，2.4 GB 要 87 分钟）。
> 可以用 `tools/fetch_parallel.py` 开 8 线程下同一个轮子，实测 **4.27 MB/s、10 分钟**：
>
> ```powershell
> python tools/fetch_parallel.py <轮子URL> tmp/torch.whl --threads 8
> pip install --force-reinstall --no-deps tmp/torch.whl
> ```
>
> **瓶颈是单连接限速，不是总带宽** —— 这个结论值得记住。

### 2. 准备语料

把年报 PDF 放进 `data/raw/`（可从[巨潮资讯网](http://www.cninfo.com.cn)下载），然后：

```bash
python src/stage2_extract.py        # PDF → 文本
python src/stage2_chunk.py          # 文本 → 分块
python src/stage3_build_index.py    # 建索引（跑一次）
```

### 3. 检索

```bash
python src/stage3_search.py         # 向量检索 + 速度对比
python src/stage4_bm25.py           # BM25 检索
python src/stage5_fusion.py         # 混合检索 + 重排
```

### 4. 生成（需要 API Key）

在项目根目录建 `.env`：

```
DEEPSEEK_API_KEY=sk-xxxxxxxx
```

然后：

```bash
python src/stage6_generate.py       # 生成带引用的答案
```

> ⚠️ `.env` 已在 `.gitignore` 中，**密钥不会被提交**。

然后打开 **http://127.0.0.1:8000**

> ⚠️ 模型加载需要 **30-60 秒**。这期间访问会 503 —— **不是崩溃**。
> 页面右上角有状态灯，显示「服务就绪」再提问。

> ⚠️ **别去 `/docs`** —— 那是 FastAPI 自动生成的 Swagger 调试台，

## 关键设计决策

| 决策 | 理由 |
|---|---|
| 手写 BM25 而不用 `rank_bm25` | 一共 40 行，自己写一遍才真懂 `k1`/`b` 在控制什么 |
| RRF 用排名而非分数 | 两路分数**量纲不可比**，直接相加会让 BM25 完全主导 |
| 只用领域词表，不换分词器 | 通用分词器不懂垂直领域，加 19 个词就能解决大部分问题 |
| 重排只处理 Top-20 | 全量 1265 条不可行（CPU 单条 1.8 秒 → 38 分钟）|
| 提示词强制拒答 | 宁可拒答也不编造——**这是 RAG 可信度的底线** |
| 生成温度设 0.1 | 问答要稳定复现，不需要创造性 |
| 模型在 `lifespan` 里**只加载一次** | 写进接口函数会导致每个请求都重新加载模型，单次 40-60 秒，服务等于不可用 |
| `/search` 与 `/ask` 分离 | 检索免费、生成花钱。分开后前端可以先展示证据，用户确认再触发生成 |
| JSON 显式声明 `charset=utf-8` | 否则 PowerShell 的 `Invoke-RestMethod` 会按 Latin-1 解码，中文变 `åæ¬éå¢` |
| 演示页的完整文本用 **CSS 折叠**而非 JS 截断 | 截断后浏览器 `Ctrl+F` 搜不到，也无法展开查看 |
| 证据文本合并换行 | PDF 提取出的文本一行一个表格单元格，不合并就是「竖排数字粥」，人类读不了 |

## 已知局限

- 语料仅 **1 家公司的年报**，所以公司名等实体 IDF 偏低，区分度不足
- **PDF 表格提取质量差**（竖排数字粥），这是当前检索噪声的主要来源，尚未做过滤实验
- 评估集只有 **32 条参与检索评估**——每答对一题 Hit@5 变动约 3%。
  **趋势可信，但小数点后两位不要较真**
- **口语化改写类只有 0.375**，且部分改写仍与原词有重叠，
  真实的语义泛化能力**可能比这还低**
- gold 定义偏窄：锚点只认「含那个数字的块」，主题相关但不含该数字的块不算命中
- 未做分块大小的对照实验（当前固定 512 字）
- **服务与评估结论还没对齐**：`/search` 用的是加权融合 + 重排，
  但评估显示 **top-5 场景下纯 BM25 更好**（0.7188 vs 0.6562）。见「下一步」
- 演示服务**无鉴权、无限流、无并发控制**，只适合本机演示
